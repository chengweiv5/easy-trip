## 本轮发现并修正的设计问题

### 原始 SSE 分片不能按 toolCallId 去重

旧架构写“重复流事件按 runId + modelTurnId + toolCallId 去重”，容易被误实现为对原始 SSE delta 去重。官方 Chat Completions 说明：首个工具 chunk 包含 id/type/name，后续 chunk 按 index 继续携带参数；同一 completion 的 id 也重复出现。[S4]

合成反例把参数分成两个 chunk：若仅保留首片，JSON 被截断；按工具索引正确累加后得到完整 query/city。该反例已运行并保存，而不是只做文档推测。

已在架构第 4.2 节收敛为：

1. ProviderAdapter 按 `attemptId + choiceIndex + toolIndex` 拼接，不按 toolCallId 去重原始 delta。
2. 完成且通过成功终止语义、JSON/schema 校验后，才产生 `ToolCallComplete`；本版保守等待成功 finish 与 DONE。
3. Runtime 只对完成的请求按 `runId + modelTurnId + attemptId + toolCallId` 去重，并核对参数摘要。
4. 重试是新 attempt，不拼接新旧流；业务写入仍用独立 operationId，不依赖模型调用 ID。

该修正不改变组件关系，所以本轮无需重画架构图。

### 如何避免“看起来成功”的误判

- 两条用例各自使用新会话；图片请求的 system/user 文本**均不包含杭州、西湖、灵隐寺**。城市/目标只在前一阶段经 OCR 和目视检查的合成图片像素中，输入是 `user` 的 text + Base64 `image_url` 内容块，没有前置 OCR 给模型。
- 首轮必须返回真实 `finish_reason=tool_calls`，只允许一个 `search_places`，并由本地程序严格验证 JSON、工具白名单、原始 city/query、排除项和调用 ID；不是由探针预填 tool_calls。
- Fake 工具从已验证参数生成无坐标候选，明确 `fixture_only=true`、`saved=false`；只在工具结果中加入每条用例独立随机的 `verification_code`。第二轮正确回显该码，证明模型消费了本轮工具返回值，而不是只重复输入。
- 第二轮均正常 `finish_reason=stop`、无额外工具调用，包含正确城市/候选与“尚未收藏”，未把被排除的灵隐寺当结果。
- 本轮真正联网的是 DeepSeek 推理 API；`search_places` 仍是 Fake，不验证真实地图 POI、坐标、高德隐私门控或 Room 事务。
- 磁盘日志不存 Authorization/key；保存请求时去掉 Base64 图体（仅留合成图 hash），不持久化 reasoning 正文。已扫描本轮证据及本轮待交付文件，未发现配置 key。密钥留在仓库外 `0600` 专用配置，不进入 Git。
