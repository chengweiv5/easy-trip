## 1. 结论与纠正

**8192是Easy Trip为第二步纯文字整理主动设置的`max_tokens`，不是DeepSeek模型能力上限。** 先前把保留8192当成必须重做输出协议的理由，约束过强。用户已确认先评估提高应用预算，本轮不再推进“引用原文＋必要差异”的协议重构提案。

新证据／实体协议可以保留，优先评估输出上限和传输预算的配套调整。Native执行方式保留，不要求用户重新选择；本轮结果仍是待确认的参数提案，不冒充已开发或真实服务验收。

## 2. 当前生产调用链

| 位置 | 实际配置 |
|---|---|
| `AssistantPlaceNormalizer.kt`的`PlaceNormalizationProtocol.request` | `max_tokens=8192` |
| `ModelPlaceNormalizer.normalize` | 通过`AssistantTransport.decodeWithRepair`调用普通`post` |
| `AssistantTransport`默认OkHttp | callTimeout=45秒、connectTimeout=15秒；read/write未显式设置 |
| 缓存的同版本OkHttp 4.12.0实际默认值 | readTimeout=10秒、writeTimeout=10秒 |
| 普通`post` | 请求6MiB，响应256KiB |
| 第一阶段`GuideBatchPolicies`官方Flash分支 | 输出32768、整次调用180秒、响应2MiB |
| 攻略最外层期限 | `180秒＋图片数×75秒`，上限1800秒；只重试整理仍经过该外层 |

因此，**只修改`max_tokens`可能依次撞上读取超时、整次调用超时、响应字节限制或外层批次期限**。第一阶段180秒不是第二阶段的实际配置，不能混为一谈。

## 4. 离线完整输出容量对照

使用上一轮保存的官方tokenizer JSON与tokenizers 0.22.2，加载纯数据、禁用额外特殊token。保留完整字段，不压缩名称或删证据。下面是400出现项／100组的**输出结构尺寸探针**，不代表来源语义已通过生产decoder或真实模型能正确生成。

| 样例 | arguments tokens | 完整HTTP响应bytes | 32K能否容纳 | 64K能否容纳 |
|---|---:|---:|---|---|
| 普通短名称 | 27,710 | 101,274 | 是，余5058 | 是，余37826 |
| 多城＋完整入口＋20个冻结锚点 | 32,476 | 120,695 | 只余292，不宜依赖 | 是，余33060 |
| 合法长度内的较长名称／父名 | 54,076 | 293,495 | 否 | 是，余11460 |
| 合成100字符入口名称／父名 | 69,276 | 342,359 | 否 | 否 |

结论：

1. 32K能解决普通样例，但对复杂结构几乎没有工具封装／输出波动余量。
2. **64K是本轮推荐的候选值**，可覆盖已测普通、复杂和较长名称场景，不必为8192推翻原协议。
3. 64K不是“所有最大长度组合必过”的证明；100字符极端组合仍超限。不能把测试上限仍为400当成已完成全部400容量验收。
4. 较长名称样例的响应已超过旧256KiB。建议新路径响应上限2MiB，仍逐字节检查，超限保留来源与成功结果，不接受半截JSON。
5. 既有1MiB恢复上限不因网络响应放大而自动改变。上轮500字符×400证据的极端快照仍超限，须保持上一有效文件和内存状态，不能截断后假称已保存。

## 5. 超时验证

使用仓库缓存的**同一OkHttp 4.12.0／Okio 3.6.0**，临时Java程序仅监听`127.0.0.1`随机端口；无模型请求、无手机或模拟器操作。

### 5.1 实际读取默认值

按生产构造方式创建client并读取getter：

- callTimeout：45,000ms；
- connectTimeout：15,000ms；
- readTimeout：10,000ms；
- writeTimeout：10,000ms。

### 5.2 本机延迟响应

同一服务等待11.5秒才开始返回：

| 配置 | 结果 |
|---|---|
| 现有client | 10,028ms后`SocketTimeoutException` |
| 候选client：call/read=600秒、write=60秒、connect=15秒 | 11,572ms成功取得完整响应 |

这证明默认读取超时确实生效，且候选设置在同版本客户端有效。**不证明真实DeepSeek 64K输出一定在600秒完成。**

### 5.3 响应边界

通过与`AssistantTransport.send`相同的Okio `source.request(limit+1)`读取方式验证：

- 256KiB恰好边界接收，256KiB＋1拒绝；
- 2MiB恰好边界接收，2MiB＋1拒绝。

这是本地读取模式测试，不是生产Android集成或最终APK验收。

### 5.4 期限选择依据与边界

复读前轮7次实际文字整理：输出415–493 tokens、耗时1.746–3.333秒，包含整次网络耗时。它们不能外推为64K的速度保证。

仅做敏感度分析：按150–250 tokens/s，27,710输出约111–185秒，65,536输出约262–437秒；**这是算术情景，不是模型测速或ETA**。因此候选整次调用600秒比180秒更有合理余量，实际仍需后续有限真实调用验证。

当前外层短图片批次会早于候选600秒结束：0图180秒、1图255秒、6图630秒、10图930秒。只延长内层会制造“高额配置已经改了但仍超时”的问题。

建议仅新证据协议官方Flash路径使用：

```text
单次整理：call 600s / read 600s / write 60s / connect 15s
攻略外层：max(既有按图数期限, 1500s)，仍不超过1800s
```

1500秒是最长允许等待，不是固定等待：最多两次600秒的既有格式补救，加约180秒提取及余量；多组/高德/极慢网络仍可能触及总期限。用户取消即时生效，禁止后台无限等待或自动第三次语义请求。正常请求结束即返回，不为凑期限增加延迟。

**把上限从8192改为65536，不等于每次费用变为8倍。** 若仍只输出原来的约500 tokens，输出部分按约500计费；允许产生更多完整结构时才会增加实际用量。后续验收必须记录服务器真实usage及所有失败／补救，不能把离线计数当收费凭证。
