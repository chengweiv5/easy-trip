## 范围与根因

- 用户明确要求“按半展开区域来计算缩放”。本轮只改助手地图视角规则，不新增页面或功能。
- 分支 `codex/v3.4-assistant-half-viewport`，基于 `5a34612ea38187b271a380b35584d849633c76fe`。修改前 fetch 与开放 PR 检查完成，候选 PR 为 0。
- 原实现使用当前抽屉的安全区域；全展开时生产布局探针得到仅 1px 高的 fit 矩形。折叠不生成新相机命令，错误缩放因而被保留。两个相邻同城坐标即可复现，异地地点不是必要条件。
- 设备红测在全展开收到两个结果时失败：期望 HALF bottom inset 1170px，实际 2292px。修复后同一测试通过。
- 未在手机重放折叠操作或测量真实 SDK zoom；前轮截图和布局探针不能冒充真机修复验收。

## 实现

1. `WorkspaceScaffold.kt` 新增助手专用布局：`fitInsets` 固定使用当前窗口的 HALF anchor，`visibleInsets` 仍使用实时抽屉高度。
2. `TripWorkspaceContent.kt` 仅助手打开时选择此布局；普通搜索保持优先，普通地点池与行程分支不变。
3. HALF 高度与抽屉一致：按可用高度缩放；大字采用同一 360dp 最低高度，并受 expanded anchor 限制。
4. 新结果与主动选点可以定位；展开、折叠、关闭、重开不重发旧相机请求。不修改相机请求 owner、通用 renderer 或原有单点 zoom。
5. 保留城市优先、100地点／20图／30天、部分成功与重试；仍为 3.4.0/build27/schema13，无数据库改动。

### 开发中失败及独立基线

- 补单点断言时误用 `SinglePoint.safeInsets`，首次全量构建编译失败；改为公开 `centerOffset.yPx` 后通过，没有修改产品 renderer。
- 初版大字测试另断言地图可用高度大于全高三分之一；大字最低 HALF 高度会合法压缩比例，两个 case 因该额外假设失败。保留精确 HALF inset 断言，将额外防退化检查改为本测试设备至少96dp，最终5项全过。产品代码不因这次测试修正而变化。
- 扩大正常尺寸测试原为11项，其中 `realNavigationEntersWorkspaceSearchesReturnsAndSwitchesSections` 在 `WorkspaceFlowTest.kt:289` 等待搜索结果超时，10项通过。
- 用本轮未修改 HEAD 的 `git archive` 在独立临时目录构建，核实两个产品文件和原测试逐字节匹配 HEAD；同一模拟器精确重跑也在第289行出现相同5秒超时。该 case 未打开助手，属已复现的基线问题，本轮不扩大修改范围，不宣称全应用全绿。
- 最终普通组为10项通过；不把去掉已证实基线失败后的专项通过冒充原11项全部通过。
