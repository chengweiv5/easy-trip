## 原因与修复

此前手机8项查询在455ms内发起，前3成功、后5报1800且均已补城市；
独立真实SDK突发探针捕获 `1800 / CUQPS_HAS_EXCEEDED_THE_LIMIT`。
手机日志未保留原始错误名称，因此手机归因仍为高度吻合；
不把所有1800视为限流。历史诊断见 `v3.2.0-assistant-search-pacing-diagnosis.md`。

本轮新增 `AssistantSearchPacer`，由 AppContainer 持有并通过 Factory/ViewModel
注入 Controller，应用内所有旅行助手复用同一个实例：

- 使用单调时钟，相邻SDK查询发起至少700ms，最多2个在等待结果的助手调用。
- 首次搜索、单项重试、新批次、多个旅行助手共享状态，不为每批重建节流器。
- 等待可取消；取消、旅行失效、撤销同意后不会继续发送排队请求。
- 排队时用户修改单项后，发起前重新核对item generation，不发送旧名称。
- 排队不占SDK单项15秒超时，整批90秒保持。
- 脱敏诊断在取得时隙后记录；诊断等待放在发起互斥区，避免慢日志导致后续请求追赶。
  日志异常/悬挂仍受既有500ms保护；没有新增原文、Key、URL或SDK消息落盘。
- 不新增自动重试、弹窗、依赖或隐式收藏；用户名称、城市确认、候选核对与收藏逻辑不变。

版本保持 **3.2.0/build25/schema11**，UI/Pencil、数据库迁移及签名配置不变。
