## 对照设计

`AssistantSearchPacingDiagnosticTest.compareInitialEightPlaceSearches` 走实际
`PlaceAssistantController → PlaceSearchDataSource → AmapPlaceDataSource → PoiSearch`。
所有组的城市、名称、查询参数、候选检查保持相同，只在公开搜索边界调整调度：

- baseline：产品现有并发2，无发起间隔；
- serial：完整SDK请求互斥，无额外延迟；
- paced：不更改并发2，发起间隔至少700ms。

每项断言READY、青州市、POI名称包含目标景点；未自动选择或收藏。
组间4秒，交叉顺序，部分组反转地点顺序。

原样控制器未复现时，增加独立探针
`inspectSdkBurstErrorMetadata`，直接调用相同SDK的同步 `PoiSearch.searchPOI()`，
使用与产品相同的query/pageSize/pageNum/cityLimit。该探针只为观察短时间突发和
`AMapException`的安全错误名称，**不是产品异步控制器的等价端到端复现**。
最多8项，只有显式参数且在模拟器才执行，原始信息按白名单输出，其他内容写为OTHER。
不输出Key、URL、响应正文、坐标或用户输入。

## 结论与边界

1. **直接验证**：同版本真实高德SDK的1800可以由请求频率超限产生；
   依据是真实异常中的`CUQPS_HAS_EXCEEDED_THE_LIMIT`，不是仅按数值1800猜测。
2. **高度吻合但未直接证明手机因果**：手机455ms内发起8次、前3项成功后5项失败，
   与频率超限一致。手机原始错误名称未记录，不能声称每个1800都代表限流。
3. **城市不是这次补丁生效问题**：手机失败项已补前缀，改名称不能消除请求频率限制。
4. **只限并发数不等于限频**：响应越快，同一时间窗越容易连续发出更多请求；
   模拟器响应慢时自然分散，解释了此前模拟器通过而手机失败的可能性。
5. **没有确认精确配额**：突发结果受服务时间窗、缓存和其他请求等影响；
   700ms是本次验证参数，不是高德承诺的通用安全阈值。
6. 本轮官方网页检索和reader未取回有效正文；未以未验证网页信息推定平台配额。

## 后续修复建议（尚未实施）

- 在助手搜索边界增加共享的请求发起节流器，以700ms作为已验证起点；
  保留最多2个进行中请求，首次、单项重试及跨批次共用，避免每次新建限流状态。
- 排队等待可取消，取消/离开后不发起旧请求，不阻塞主线程；开始SDK请求后才计算单项15秒超时。
- 不改用户名称、城市确认、地图核对、选择或收藏写入行为。
- 不把所有1800静默无限重试。若再加入重试，必须限制次数、退避，
  明确瞬时错误白名单及错误元数据获得方式；不可将Key/权限/参数错误伪装成暂时失败。
- 补快速SDK桩的控制器回归（如200ms成功、每短窗超额返回1800），验证
  首次8项、20项上限、取消排队、失败后重试、快速重复提交和零隐式收藏。
  桩只能锁住调度行为，最终还需真实SDK和获准后的手机首次搜索验收。
