## 2. 当前事实与方案取舍

基线为`5a34612ea38187b271a380b35584d849633c76fe`，应用来自`633703a686a60a8465601eb515aa697cc4328836`。本轮开放PR检查为0，640项输入与已交付版本一致。

当前：

- `AssistantInputProcessor.parse`先等待正文，随后在普通`for`循环内等待每张图片；网络请求没有使用高德节流器。
- `ImageToolProtocol`只接收一张`PreparedImage`，提示词和来源映射都假设单图。

- 原v3.3规格将逐图解码、节约内存和逐图网络等待绑在一起；新设计将本地图片准备与网络调度分离。
- `AssistantSearchPacer`实际为700ms发起间隔＋最多2个在途，而非必须等上一次高德响应后再开始。

方案比较：

| 方案 | 取舍 |
|---|---|
| 仅单图并发 | 容易改，但正文＋N图仍有N+1次提取，不能跨图理解；不采用为主路径 |
| 一次无限量提交全部素材 | 减少调用，但超大请求、内存与失败范围不可控；不采用 |
| **按字节预算合并，超过才分组并发** | 普通帖一次提取，大帖有界处理，保留每源结果；采用 |

保留独立语义整理是为了复用已验证的别名、泛称、父子地点保护和增量合并逻辑。多图提取不新增第二套“直接完成收藏”的快捷路径。是否把提取和语义整理进一步合成一个模型响应不在本轮范围。

## 3. 数据流与职责

```text
已有链接读取／下载／归属校验
  → 逐张准备图片到App私有临时文件
  → 按实际请求字节组包（普通攻略1组）
  → 最多2组同时向模型请求，无700ms等待
  → 每组响应按正文／图序号独立校验并保存成功缓存
  → 本轮各组终态后，复用一次全局语义整理
  → 现有高德节流匹配 → 手动标记／收藏
```

依赖关系必须真实：提取请求之间独立；语义整理依赖本轮已完成提取；高德依赖整理结果。部分组失败不会阻止成功组进入整理；仍在运行的组可在有界时限内完成或被取消，不引入边接收半段JSON边查询的未验证结果路径。

职责边界：

- **素材准备与组包**：稳定来源清单、临时文件、字节预算、确定性分组；不访问地图或写收藏。
- **多素材协议**：正文与多张图的同一请求、每源回执、单源证据校验；不信任模型生成的本地ID、路径或操作。
- **模型调度**：应用级最多2个攻略合并提取请求在途，生命周期／取消／格式补救；与高德调度相互独立，其他既有入口不改调度。
- **输入处理器**：输出仍可归并为`ParsedSource`，复用当前成功缓存、部分失败和恢复流程。
- **控制器与整理器**：保留用户编辑、POI、选择、幂等回执和现有最终去重；不重构无关模块。

## 4. 请求预算、组包与内存

### 4.1 本轮选择的预算

| 项目 | 设计值 |
|---|---|
| 已核验的官方`api.deepseek.com`／`deepseek-flash`合并请求 | 完整HTTP body最多16MiB |
| 其他已配置OpenAI兼容服务 | 默认保留6MiB body预算；不假设支持官方服务的更高限制 |
| 模型组请求在途数 | 全应用最多2，包含该请求的格式补救；无固定发起间隔 |
| 合并提取调用超时 | 180秒；连接仍15秒；不改变普通入口的现有超时 |
| 官方Flash合并提取输出预算 | 32768 tokens，支持最多400候选的结构化回执；不是召回保证 |
| 其他兼容服务合并提取输出预算 | 保留8192 tokens；输出截断明确失败，不把部分输出当完整结果 |
| 合并提取响应体安全上限 | 2MiB；普通协议继续现有256KiB |
| 全批处理期限 | 保留现有按图片数计算、最多30分钟；不以无限延长超时代替并发 |

预算为产品实现选择，不是供应商额度承诺。未识别的服务不猜测更高额度；HTTP拒绝时保留明确原因，不静默改模型、换服务或自动改成单图重发。

16MiB是在模型上限内留余量的App预算，不是按“最多几张”分组。最终是否一个请求取决于图片实际字节、正文、提示词、schema和Base64开销。若原6图／10图实例均在预算内，必须各一次提取；不能为了实现方便固定每2／4／6张拆组。

### 4.2 确定性组包

1. 正文与图片保留稳定sourceId和原帖ordinal；只准备本次需要重新识别的图片。
2. 沿用单图4MiB、长边4096、像素限制与现有质量策略，不为凑一个请求额外缩成难以阅读的小图。
3. 正文默认作为第一个提取目标，图片按原顺序加入。组包计算**完整UTF-8 HTTP body**，包含`4 × ceil(n/3)`的Base64长度、JSON转义、schema、上下文与格式补救预留。恰好达到预算允许发送，超过1字节即分组。
4. 不同组的正文上下文、城市上下文必须一致，但正文作为提取目标只出现于一组；其他组只将其视为理解上下文，不重复产出正文来源。
5. 单张准备失败只标记该源，其他素材继续组包；单源不能装入任何组时明确该源失败，不能删除整批。
6. 格式补救请求再次做完整预算校验，不能绕过预算。预算本身不授权多次网络重发。

### 4.3 有界内存与文件

沿用逐张解码，但准备后的压缩图写入App私有临时文件，不把20张Bitmap或全部Base64常驻内存。请求按流写入私有临时body文件，发送时流式读取，避免完整JSON字符串＋UTF-8＋Base64的多份复制。

- 图像解码同一时刻1张；全批准备文件最多80MiB（20×4MiB），不改变原素材30MiB入库上限。
- body临时文件最多两个在途＋一个待发；官方策略最多48MiB，其他服务按对应预算计算。保留文件长度但不提前创建无限队列body。
- 发送失败／取消后删除本次body文件和可重建的准备文件；原攻略、成功解析缓存及失败状态保留。旧批清理不能删除新批文件。
- 恢复时不自动重放网络请求；临时body不是恢复依据。持久缓存不保存Base64、凭据、绝对临时路径。
- 磁盘不足、损坏、取消的资源释放必须有测试；不得捕获OOM后继续大量分配，也不以关闭安全检查兜底。

## 5. 多素材返回协议与来源校验

一个响应可以包含多个来源的完整结果。结构表达为：

```json
{
  "sources": [
    {
      "sourceId": "text",
      "status": "OK",
      "items": [
        {
          "query": "原文中的地点名",
          "city": "",
          "sourceSpan": "包含该地点名的原句",
          "uncertain": false
        }
      ]
    },
    {"sourceId": "image_2", "status": "NO_PLACES", "items": []}
  ]
}
```

这只是协议形状，不是可直接发送的产品提示词。最终实现将schema和校验规则统一定义：

- 请求声明本组唯一允许的目标来源，模型必须逐源确认一次；来源token由本地生成并映射回真实imageId和ordinal。
- `OK`／`NO_PLACES`／`UNREADABLE`／`OVERFLOW`为明确来源状态；`NO_PLACES`是完成但无地点，失败不得伪装成无地点。
- `OK`必须提供完整且可校验的items，`NO_PLACES`必须空数组；`UNREADABLE`和`OVERFLOW`不接收部分候选。
- 正文证据必须命中本次真实正文，摘录不超过500字符，不把整篇正文复制到每个候选；图片候选必须具备原图可读名称、targetBasis／targetDetail／entityRole／parentName等现有证据。来源ID归属校验不等于独立OCR核验图片事实。
- 图片prompt由“本张图片”改为“每个来源分别引用证据”；城市可参考完整攻略及明确城市上下文，但不能把图1的字冒充图2证据、凭城市常识补地点或混入底图背景。
- 同一地方在不同来源出现时分别保留来源，不强行要求提取阶段跨图去重；后续统一整理合并。
- 附加字段、普通PLACE父级空值、已知枚举大小写及完整stop工具调用继续兼容。关键字段、来源事实及证据不靠猜测补齐。
- 单源内部仍是全有或全无：一项不符合关键证据则该源失败，不悄悄丢掉这一项后将该源标成功。其他可独立定位且完整校验的来源继续成功。
- 未知sourceId的项不使用；缺失的预期来源标失败。重复ID使该ID对应来源失败。已知且唯一、结构完整的其他源仍可接受；无法解析整体结构或无法可靠定位来源时整组失败。
- 响应截断、非完整JSON、多工具歧义等无法证明完整性时，整组不接收；不抢救半段JSON。
- 每源100、全批400候选与最终100地点上限保留；统计跨组、缓存与重试结果，不通过拆组绕过上限，不静默截断。

## 6. 失败、重试、取消与恢复

### 6.1 部分失败

本地坏图、有效响应中的单源不可读、缺失回执或关键校验失败按来源显示。组级超时／HTTP错误／截断影响该组尚无有效回执的来源，不自动归咎于某一张图片。其他组成功缓存不撤销。

无法获得完整响应时不能承诺“同一请求中的成功图片也能抢救”；这是合并请求的明确取舍。全组传输失败会保留该组素材供用户重试，不能假装已拿到未返回的地点。

### 6.2 格式补救与手动重试

- 可修复格式问题最多补救一次；有效多源响应只补救其中可修复的失败来源，已经接受的成功来源不再作为提取目标。
- 网络、鉴权、限流、截断、来源事实错误不自动重发；不自动拆小重试掩盖费用或未知发送结果。
- 用户点击重试只选择失败／取消来源，按同一预算重新组包。图片重试仍可携带正文作为上下文，这可能产生上下文费用，不能承诺正文完全不再传输。
- 全部组完成或失败后，对成功＋缓存候选运行一次统一整理；若只是整理失败，单独重试整理，不重新发送图片。
- 返回顺序不能决定地点字母和归并优先级：按稳定来源顺序及来源内顺序归并，保留已有行ID与用户修改。

### 6.3 取消与关键服务错误

- 取消后停止排队与在途请求，已发送内容不可撤回；仅保留已完整校验且归属于当前代次的结果。迟到响应不覆盖新输入／新城市／新旅行。
- 在途多个组中出现鉴权或明确图片能力错误时，停止尚未发出的组并标明未发送；其他已在途组的发送事实与已完成结果如实保留。
- UI进度必须区分未发送、请求可能已发送、已接受结果；同组多个图片同时“理解中”是正常表现，不伪造逐图网络请求。
- 对现有图片准备锁、模型在途锁、状态更新协程的顺序做死锁／取消测试；不能用共享可变list在多个回调中无保护写入。

### 6.4 持久化与收藏

缓存仍以源ID、原素材及提取时城市为依据，不以易变化的分组编号为身份。旧version1恢复记录继续可读；若需要新的可选字段，旧字段语义不变，不升级数据库schema。

2MiB网络响应上限不等于恢复记录上限。保留当前1MiB恢复记录限制，只保存转换后的领域结果、不存原始响应；写入前测量完整UTF-8字节。若超限或落盘失败，保留上一份有效记录和当前内存结果，明确提示本轮结果尚未完整保存，不能宣称杀进程后可恢复，也不为满足大小静默裁剪候选、来源或已收藏回执。现有Room收藏事务仍独立幂等，恢复写失败不能触发重复收藏。

部分收藏继续使用独立`guide-partial:`回执，不结束攻略；重试后保留已收藏、手动名称／城市／分类、选择和既有POI，仅查询新增。全部处理完成后收藏才进入空白新一轮。

- 请求预算内的原例必须一次多模态提取；若实际超过16MiB，则记录实际字节和拆组依据，不降低清晰度凑数。
