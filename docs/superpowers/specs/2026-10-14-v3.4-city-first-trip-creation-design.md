日期：2026-10-14（Asia/Shanghai）。状态：**用户已确认本文与 C 系列 UI；串行实施和限定范围验证完成，未提交／推送／安装手机／发布。**

本文替代 2026-10-13 规格中“先识别地点、查地图、选择地点，再创建并收藏”的主流程。旧规格、G 系列画板及旧实现保留为历史证据和兼容恢复路径，不再作为新创建入口的行为依据。

## 1. 用户意图与范围

用户通常先发现攻略，此时还没有旅行。全局助手应先从攻略确定目的地，确认后创建旅行，再自动进入这趟旅行的助手并发送原攻略。后半程完整复用已有旅行的识别、地图匹配和手动收藏，避免两套地点操作流程。

已确认的路径：

**首页助手创建 → 粘贴攻略 → 识别目的地 → 确认城市、名称、可选日期 → 创建并导入攻略 → 旅行内助手自动处理 → 用户选择并收藏。**

- 保留一次“创建并导入攻略”确认，不在模型返回城市时直接写库。
- 全局阶段不构造地点候选、不查询高德、不要求逐项核对地点。
- 创建成功时允许地点池为空。导入失败、取消、零有效地点均不自动删除旅行。
- 日期可选，仅解析用户自己补充的计划；攻略“三日游”、作者日期、截图水印和分享时间都不是用户出行计划。
- 首批仍为携程、小红书；文字和用户上传图片的已有入口不撤回。
- 100 个最终地点、20 张图片、每批 1 条链接、1–30 天空白行程日保持。地点编号至 CV、超过 100 不截断、700ms 发起间隔与并发 2 保持。
- 不新增语音、系统分享接收、聊天会话列表、自动排程或自动收藏。
- 首页左右对齐的“助手创建／手动创建”不改；已有旅行从原入口进入助手的操作不增加步骤。

## 2. 方案与取舍

| 方案 | 结论 |
| --- | --- |
| 修补全局“城市核对＋地点选择”，仍先选地点后创建 | 不采用。不能解决用户要求的职责拆分，仍有两套操作状态。 |
| 城市识别后立刻后台创建，不经确认 | 不采用。误判目的地会产生用户未确认的旅行。 |
| 城市信息准备＋一次创建确认＋持久交接给旅行内助手 | **采用。** 全局更简单，导入失败留在真实旅行中重试。代价是明确允许创建后暂时为空的旅行。 |

这次改变的是创建顺序和交接，不是重写已验证的地点识别规则。

## 3. UI 与行为

### 3.1 全局输入

- 标题“旅行助手”，说明“从攻略创建旅行”。
- 粘贴只填输入框，不自动联网；主操作为“识别目的地”。
- 保留文字、分享链接、图片与现有模型设置入口。
- 点击后读取攻略，状态为“正在识别目的地”；可取消。此阶段不展示地图、地点数量或候选列表。
- 正文和用户补充文字分别保存，不能把分享标题误当作用户本人计划。
- 模型未配置、链接读取失败或本地图片失效时，保留输入并原地处理；不创建旅行。设置返回后不自动触发首次识别。

### 3.2 精简创建确认

字段顺序：

1. 目的地城市：识别后预填，可编辑；支持多城市。
2. 旅行名称：根据目的地建议，可直接修改；不再增加名称下方说明。
3. 出行日期（可选）：未提供则保持未定，可修改或清空。
4. 旅行天数：沿用 1–30 天，默认 1 天；不把攻略标题天数自动填入。
5. 出行方式：沿用灵活出行／自驾。
6. **创建并导入攻略**。

不展示“已选地点数”“更改地点”或“地点将收藏”的摘要，也不恢复已被用户删除的日期识别成功提示卡。

- 无城市：只在城市字段就地提示，补齐前不能创建。
- 多城市：显示完整城市集合；用户可编辑为真实目的地范围，不能偷偷取第一城。
- 名称为空或天数非法：就地报错并保留表单。
- 日期歧义／解析失败：只影响日期字段，允许手动选择或保持未定继续创建。
- 返回输入页保留攻略和手动修改；更换攻略后重新识别，不将旧城市静默带入新素材。
- 创建中字段和重复提交锁定，结果以持久回执为准。不能一边报告取消／失败，一边留下已创建但不可恢复的旅行。

### 3.3 旅行内自动导入

创建提交成功后：

1. 取得持久化的真实 `tripId`。
2. 移除全局创建页的活动提交入口，导航到该旅行。
3. 通过现有 workspace 的标准助手打开动作展开面板，而不是只改 `isOpen`。
4. 带入原始分享文本、原链接／用户图片、用户补充文字及已确认的城市范围。
5. 待宿主、模型配置和地图授权满足条件后，自动领取并发送这次交接一次。
6. 使用现有旅行助手的完整生产管线；结果在当前旅行选择、匹配、纠错、重试和收藏。

不要求重新粘贴、不增加一次普通“发送”点击。若授权尚缺，先显示现有授权入口；用户完成授权回来且该交接**尚未发送**时自动继续。若模型配置失效，进入已有设置；同样只允许未发送的交接继续，不重复发送已领取批次。

收藏仍由用户点击；成功后沿用现有清空本轮规则。关闭助手只是收起，不撤销旅行，也不因重新打开而重发攻略。

### 3.4 失败与恢复

| 状态 | 行为 |
| --- | --- |
| 创建前退出 | 明确放弃才清理本会话草稿；未创建旅行。 |
| 创建确定失败 | 保留城市、名称、日期和攻略；重试相同创建操作。 |
| 创建结果未知 | 先查持久回执，不先生成新 ID 或再次创建。 |
| 已创建、交接仍待发送 | 恢复到该旅行；条件满足后领取一次。 |
| 交接已领取、进程中断、无法确认请求是否发送 | 展示“上次导入已中断”，由用户主动重试，不自动再请求模型。 |
| 导入失败／取消／零有效地点／超过100 | 保留旅行和原攻略，走旅行内既有重试或分批入口；不删除旅行、不重新创建。 |
| 已完成导入 | 恢复已有结果或收藏后的空白新轮；不重发原攻略。 |
| 已创建旅行后来被删除 | 告知不存在，不凭旧回执复活；用户重新发起新流程才算新操作。 |

“自动发送一次”指同一交接只自动领取一次；无法在客户端崩溃和远端模型之间保证网络请求严格 exactly-once。未知状态采取人工重试，而不是用重复请求换取表面上的自动恢复。

## 4. 城市识别与上下文

### 4.1 独立的目的地识别阶段

新增专用目的地解释器，输出城市集合、名称建议和可核验的来源片段；不输出 POI、坐标、地点候选或收藏命令。固定 system prompt 不含具体旅行名称、城市或景点示例，实例数据只在 user 内容中提供。

- 优先从攻略标题／正文和用户明确旅行意图获取目的地证据；必要时读取配图中的作者说明。
- 地图底图背景、途经地、作者所在地、商家推广、分享参数均不能单凭出现即变成目的地。
- 允许有证据的城市推断，但同名、歧义或证据不足应为空／待核对，不伪造确定城市。
- 用户手动确认值优先；异步返回不得覆盖人工修改。
- 沿用已有链接域名校验、重定向与读取安全规则，不绕过登录或平台访问限制。
- 城市阶段不调用完整地点 parser 或 normalizer 后再从地点反推城市。

目的地请求与日期识别是两个职责。日期阶段仅接收已区分来源的用户自述，保留固定参考日期／时区和现有本地日期校验。

### 4.2 传入旅行内助手

- 城市范围是独立结构化上下文，不靠旅行名称字符串或手机定位间接恢复。
- 单城作为该导入批次的默认搜索城市；单项明确写出的不同城市不能被覆盖。
- 多城传递完整范围，要求地点识别按证据输出各自城市；未能判断的个别项才进入现有待核对状态。
- 不给所有缺城市地点硬套第一城，不借手机位置或最近旅行兜底本次新旅行。
- 城市范围作为旅行的助手上下文持久保存，重命名旅行不丢失；人工指定的批次城市仍优先。
- 普通既有旅行无这类上下文时，保留现有默认城市策略。

### 4.3 素材复用

原分享文本／URL必须原样交接。城市阶段读取成功的正文、图片缓存可通过内容摘要和素材句柄移交，避免无意义的第二次下载；缓存是优化，不是第二套解析流程。

旅行内依然调用同一输入处理入口完成地点识别、作者证据、语义去重、餐饮过滤、高德匹配和收藏。缓存失效时通过同一个读取器重读；用户改了链接／图片则缓存失效，不能混用旧素材。

## 5. 组件和持久化边界

已核对当前源码：

- `GlobalAssistantRoute` 当前绑定新旅行目标的地点识别控制器，需要替换为“城市信息准备＋创建确认”。
- `AppNavigation` 的 `onCreated` 目前仅跳转旅行，没有原攻略交接或自动打开助手。
- `TripWorkspaceRoute` 有完整 `AssistantWorkspace.onOpen` 协调逻辑，必须复用。
- `CreateTrip` 已支持可空日期和稳定 requestId，但不携带城市信息。
- 旧 `TripCreationCommand` 要求至少一个地点，不能为了空旅行而悄悄放宽旧命令并误读旧恢复记录。
- schema12 的独立创建回执无旅行外键，保留“删除后不复活”的基础。

建议模块：

| 模块 | 单一职责 |
| --- | --- |
| 目的地解释器 | 从本批可信来源信息提取城市及名称建议。 |
| 全局创建草稿状态 | 管理输入、目的地、可选日期与人工编辑，不持有地点候选。 |
| 城市优先创建服务 | 确认后原子写旅行、空白日、城市上下文、创建回执和待交接记录。 |
| 旅行助手交接协调器 | 依据真实 tripId、宿主就绪与持久交接状态，展开助手并领取一次。 |
| 既有旅行助手 | 原生产识别、查询、纠错、收藏与批次清理。 |

### 新命令及数据库兼容

- 城市优先创建使用新的命令／日志版本和独立 operationId 命名空间，旧“创建并收藏”命令及回执解码保持兼容。
- 创建旅行、空白日、目的地上下文和 `PENDING` 交接在同一事务完成；任何一步失败不得留下缺交接的半成品。
- 继续使用无旅行 FK 的创建回执语义，校验 operationId、tripId 和规范化摘要；同 ID 不同内容必须拒绝。
- 目的地上下文与交接需要独立持久存储，建议新增按 tripId 关联的表；旅行删除时清理素材与交接，创建回执保留防复活。
- 实施预计需要 **schema12→13 的增量迁移**，只新增必要表，不重写旧表、不清数据。本轮仅规格建议，实际版本与 schema 尚未更改。
- 交接字段至少包含版本、operationId、tripId、原输入及素材句柄、已确认城市范围、摘要和状态。网络请求前原子 `PENDING→CLAIMED`；成功／取消／中断有明确持久状态。
- 不把大图、凭据或整个输入塞进导航 route；导航只传稳定 ID，数据从受控存储读取。
- 本地图片只清理本会话拥有且无人引用的文件。待交接素材不能被全局页清理误删。
- 未决日志沿用不小于现有 1MiB 有界策略；超限完整拒绝，不截断。用户源码内容不写入普通诊断日志。

## 7. 开发前验收清单

本节是未来开发门禁，本轮未执行设备、模型或数据写入测试。

- 两条用户平台样例先只提取城市，再确认创建、自动进入真实旅行助手、导入并手动收藏。
- 单城缺省补全、多城逐项归属、用户城市编辑不被定位／异步结果覆盖；无城市不创建。
- 纯分享标题“三日游”不自动填用户天数；作者日期／shareTime不填出行日期；仅用户意图可预填。
- 未配置模型、缺地图授权、读取失败、图片失效、零有效地点、超100全部保留正确阶段。
- 双击、旋转、返回重进、进程中断、创建事务失败、已领取但请求结果未知、已完成后恢复不重复创建／自动发送。
- 旅行删除后不复活；创建后改名称／日期不被旧回执覆盖。
- schema12→13 保留已有旅行、收藏、旧创建与导入回执；旧未决日志可恢复，不降级。
- 100地点至CV、20图、700ms／并发2、8192输出预算、180秒普通文字批次、1MiB日志保持回归。
- 保留原旅行内助手默认城市、收藏后新轮、地图视角和手动创建等回归。
- 320dp、2倍字体、长城市／旅行名、键盘、返回、TalkBack分别记录是否实际验收。
- 真实模型及地图测试须显式预算和隔离数据；安装、提交、推送、发布分别依据后续用户授权。
