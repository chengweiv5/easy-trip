# Easy Trip 旅行设置与日期正确性收敛设计

## 1. 目标

本阶段收敛现有旅行设置与日期范围修改流程的正确性、并发语义和验收证据，不重做已经存在的设置页面或日期领域能力。

完成后必须保证：

- 工作台“更多”继续直接进入当前旅行的设置页；
- 本阶段固定旅行开始日期，只允许调整结束日期；
- 用户尚未提交的日期草稿不会被 Room 新 emission 覆盖；
- 日期预览、确认和应用绑定同一份不可变请求快照；
- 同一个确认最多执行一次日期变更；
- 日期变更完成以最新一条 eligible fresh Room 事实为准，不以 service 返回或历史匹配 emission 单独判定成功；
- 旅行日期范围最多 30 天，创建与设置修改共享同一领域上限；
- 缩短日期前展示精确影响，事务执行前重新核对影响；
- 影响已变化时拒绝旧确认，不静默执行不同于用户确认内容的删除；
- 缩短日期正确级联删除超范围日期的行程项和 RouteLeg，保留 SavedPlace；
- 剩余旅行日保持连续编号；
- 设置入口、修改、取消、确认、失败恢复和返回在自动化及 Mate 60 Pro 真机上可达。

## 2. 范围

### 2.1 包含

- 复用现有 `TripSettingsRoute`、`TripSettingsContent`、`TripSettingsViewModel`、`TripDateRangeService` 和 Room 日期事务。
- 明确 Room 持久化基线与用户日期草稿的所有权。
- 增加显式 dirty、请求 generation 和互斥提交阶段。
- 将日期预览和应用绑定到不可变请求快照。
- 加固增长、缩短、单日删除的乐观并发和级联删除测试。
- 提交期间锁定会改变请求语义或造成虚假取消的交互。
- 修复设置页测试与生产文案漂移。
- 补“工作台更多 → 当前旅行设置 → 返回原工作台”的真实导航测试。
- 完成自动化候选门禁和 Mate 60 Pro 关键路径验收。

### 2.2 不包含

- 地图服务授权和定位权限修复；该范围进入下一独立批次。
- 设置页视觉重做。
- 修改旅行开始日期。
- 日期整体平移、头部日期删除或任意首尾编辑。
- 395dp 到 396dp 的 Sheet 锚点连续性。
- 横屏、分屏、极窄屏和 2× 字体的完整响应式优化。
- 新增旅行统计、地点统计或其他当前领域模型未提供的数据。
- 重构应用导航架构。

## 3. 当前基线

当前生产代码已经具备本阶段所需的主要结构：

- 设置路由为 `trips/{tripId}/settings`；旅行列表和工作台均可进入。
- 工作台顶栏“更多”当前直接派发 `OpenSettings`，无需新增菜单层。
- 设置页已有重命名、出行方式、整体日期范围、旅行日列表、日期缩短确认和单日删除确认。
- `TripDateRangeService` 已提供 `preview/apply`。
- `DateRangeApply` 已携带旅行日和影响计数快照。
- Room 事务已能复核旅行日、删除尾部日期并重排。
- 单日删除已有影响预览、事务复核和失败后重新检查。

现有主要缺口：

1. Room 更新在普通编辑阶段可能覆盖用户尚未提交的日期草稿。
2. preview 的 generation 保护不能完整表达 apply 的副作用身份和完成条件。
3. apply 返回与 Room 事实确认之间缺少统一的忙碌和恢复语义。
4. 日期范围乐观并发、级联删除和重编号的 Room 集成覆盖不足。
5. 设置页测试存在与生产文案漂移的断言。
6. “更多”入口仅有局部动作测试，缺少真实导航往返证据。

## 4. 已确认产品规则

### 4.1 设置入口

工作台右上角“更多”在本阶段保持为当前旅行设置的直接入口，不改为组合菜单或个人中心入口。

### 4.2 日期编辑

- 用户于 2026-08-28 明确选择旅行日期范围最多 30 天；创建旅行和设置页日期范围修改统一使用 `MAX_TRIP_DAYS = 30`。
- 开始日期固定，不在本阶段提供编辑入口。
- 用户只调整结束日期。
- 增长日期范围时，只在尾部追加连续旅行日。
- 缩短日期范围时，只从尾部删除旅行日。
- 不自动迁移被删除日期中的行程内容。
- 不要求用户先手动清空被删除日期。

### 4.3 危险操作

以下操作必须先展示影响并确认：

- 缩短日期范围并删除旅行日；
- 删除单个旅行日。

确认内容必须说明：

- 将删除的旅行日数量；
- 将删除的行程项数量；
- 将删除的 RouteLeg 数量；
- SavedPlace 将被保留；
- 操作是否可撤销。

用户确认的影响与事务执行前重新核对的影响不一致时，旧确认立即失效。

## 5. 状态所有权

### 5.1 持久化基线

`TripSettingsViewModel` 持有 Room 最近一次成功发布的日期基线：

- 当前旅行开始日期；
- 当前旅行结束日期；
- 当前旅行日 ID 和顺序；
- 用于确认提交完成的版本身份或等价快照。

Room 是持久化事实来源，但 Room emission 不自动拥有用户正在编辑的草稿。

### 5.2 用户草稿

ViewModel 独立持有日期草稿：

- 固定的开始日期；
- 用户选择的结束日期；
- `isDateRangeDirty`；
- 当前校验错误。

更新规则：

- 草稿未修改时，Room 新基线同步到草稿。
- 草稿已修改时，Room 只更新基线，不覆盖草稿。
- 当前旅行被删除时，关闭设置目的地，不保留悬空草稿。
- 提交完成并收到匹配 Room 事实后，使用新基线重置草稿和 dirty 状态。

`isDateRangeDirty` 必须是显式状态，不能仅以当前值是否等于基线临时推断整个异步流程的所有权。

### 5.3 阶段状态

逻辑阶段为：

```text
Idle
Editing(draft, baseline)
Previewing(request)
AwaitingConfirmation(request, impact)
Applying(request)
ApplyFailed(draft, reason)
```

实现可继续使用现有数据类，不强制改成 sealed hierarchy，但必须满足：

- 阶段互斥；
- 每个异步阶段绑定请求身份；
- UI 能从状态明确判断哪些交互被锁定；
- 旧阶段完成不能覆盖新一轮编辑。

## 6. 不可变请求快照

用户提交日期变更时，ViewModel 从当前基线和草稿生成不可变请求。请求至少包含：

- `tripId`；
- 基线开始日期和结束日期；
- 草稿结束日期；
- 预览时的全量旅行日 ID 和顺序；
- 预计删除的尾部旅行日 ID；
- 预计删除的行程项数量；
- 预计删除的 RouteLeg 数量；
- 保留 SavedPlace 的事实或计数；
- 请求 generation。

请求一旦进入 preview、confirmation 或 apply，不再随 Compose 输入或后续 Room emission 变化。

### 6.1 增长

增长不需要危险确认，但仍使用不可变请求和 Room 事务复核：

1. 校验结束日期不早于固定开始日期；
2. 生成目标日期范围和当前旅行日基线；
3. 进入 `Applying`；
4. Room 事务核对基线后在尾部追加旅行日；
5. 等待匹配的 Room emission；
6. 重置草稿和 dirty 状态。

### 6.2 缩短

缩短流程：

1. 基于当前基线和草稿生成请求；
2. 查询精确影响；
3. 进入 `AwaitingConfirmation`；
4. 用户确认后提交同一请求及影响快照；
5. Room 事务重新核对日期、旅行日 ID、尾部删除集合和影响计数；
6. 一致时原子删除并重编号；
7. 不一致时拒绝旧快照并要求重新预览；
8. 成功后等待匹配的 Room emission。

确认弹层不得在显示期间重新解释最新草稿；它只展示自身绑定请求的影响。

## 7. 提交与完成语义

### 7.1 提交互斥

进入 `Applying` 后：

- 锁定日期输入；
- 锁定确认按钮；
- 忽略重复提交；
- 锁定系统返回、顶部返回、弹层外部点击和取消；
- 不显示无法保证撤销数据库事务的“取消提交”入口。

同一个 request generation 最多调用一次日期 apply。

### 7.2 完成条件

service 或 repository 调用返回成功只说明写入调用完成，不单独关闭忙碌状态。

最终成功要求：

1. apply 调用成功；
2. 后续成功 Room emission 与请求目标日期范围匹配；
3. 旅行日数量、顺序和结束日期符合请求结果。

每条满足 request generation、collector generation 和 emission version 门槛的 fresh emission 都覆盖当前匹配事实：匹配写入 `true`，不匹配写入 `false`。因此 service 返回时只接受最新事实；曾匹配后又出现 fresh mismatch 不得清 dirty 或误报成功，而应继续等待后续匹配事实，或在流失败/耗尽时进入同步失败。

只有三个条件同时满足，ViewModel 才能：

- 退出 `Applying`；
- 更新 baseline；
- 用 baseline 重置 draft；
- 清除 dirty；
- 关闭确认状态；
- 发布成功反馈。

### 7.3 流恢复

若 apply 已成功，但用于确认的 Room 流暂时失败：

- 保留请求身份和“写入已成功、等待同步确认”的上下文；
- 退出不可恢复的永久 busy；
- 提供重新同步入口；
- 重新同步只重订阅或重新读取 Room；
- 不再次执行 apply；
- 旧 collector 结果使用 generation 隔离。

该语义与旅行删除的“写入一次、同步确认可重试”原则一致，但不得为了复用而引入不匹配的通用状态抽象。

## 8. 错误处理

### 8.1 输入错误

- 结束日期早于固定开始日期时不生成 preview 或 apply。
- 日期范围超过 30 天时显示“旅行最多 30 天”，且在查询删除影响或执行 apply 前拒绝。
- `TripService` 与 `RoomTripRepository` 的创建、插入/追加旅行日入口，以及 `RoomTripRepository.applyDateRange` 均防守 30 天上限，避免内部调用绕过 UI；29→30 成功，30→31 必须在写入前拒绝且状态不变。
- 日期差先以 `Long` 计算并校验 `1..30`，再转为 `Int`，极端日期不得溢出或创建海量旅行日。
- 有日期旅行还必须满足 `startDate + dayCount - 1` 可表示；领域 helper 统一验证 inclusive end date。`LocalDate.MAX` 的 1 日旅行有效，2 日旅行以“日期范围超出支持范围”拒绝，Validator、Service、Room create、`setStartDate` 及后续插入共同防守；Room 的 `setStartDate` 必须在同一事务读取 trip/day count 并在任何写入前校验。
- 错误显示在日期字段附近。
- 修正输入后可重新提交。

### 8.2 预览失败

- 保留草稿和 dirty 状态。
- 退出 `Previewing`。
- 显示可重试错误。
- 重试生成新 generation，不复用不完整影响。

### 8.3 快照失效

事务发现以下任一变化时拒绝旧快照：

- 旅行日期基线变化；
- 旅行日 ID 或顺序变化；
- 待删除尾部集合变化；
- 行程项或 RouteLeg 影响计数变化。

UI 提示“旅行内容已变化，请重新确认”，保留用户目标结束日期并重新生成影响。旧确认不得直接再次 apply。

### 8.4 应用失败

- 保留草稿和 dirty 状态。
- 退出 `Applying`。
- 不展示成功反馈。
- 若失败发生在写入前，可重新 preview/apply。
- 若无法判断写入是否完成，先重新读取 Room 事实；禁止盲目重复 apply。

### 8.5 旅行被删除

当前 trip 从 Room 消失时：

- 停止设置流程；
- 清理本地确认和提交状态；
- 返回旅行列表；
- 不尝试恢复对已删除 trip 的草稿。

## 9. 单日删除

单日删除继续沿用现有能力，并与日期缩短保持一致的原则：

- 最后一个旅行日不可删除；
- 删除前查询精确影响；
- 确认绑定 day ID、影响计数和 generation；
- 事务重新检查旅行日仍存在、不是最后一天、影响未变化；
- 删除后级联清理该日行程项和 RouteLeg；
- 剩余旅行日连续重编号；
- SavedPlace 保留；
- 事务失败或快照失效后重新预览，不直接重放旧删除。

本阶段不把日期缩短和单日删除合并成一个新的通用框架；只统一行为原则和测试契约。

## 10. 组件边界

### 10.1 `TripDateRangeService`

职责：

- 校验日期范围；
- 生成影响预览；
- 构造或传递不可变 apply 快照；
- 调用仓储 apply。

不负责：

- Compose 草稿；
- dirty 判断；
- 导航；
- 成功反馈消费。

### 10.2 `RoomTripRepository`

职责：

- 在单一事务内重新核对快照；
- 尾部追加或删除旅行日；
- 级联维护行程项和 RouteLeg；
- 保持连续 dayIndex；
- 拒绝过期或不一致的请求。

Room 事务是最终写入权威，不能信任 UI 已完成的预览核对。

### 10.3 `TripSettingsViewModel`

职责：

- 持有 baseline、draft、dirty 和阶段；
- 生成并追踪 request generation；
- 启动 preview 和 apply；
- 拒绝旧异步完成；
- 协调 apply 返回与 Room 事实确认；
- 提供重新预览和重新同步行为；
- 发布一次性导航或反馈 effect。

### 10.4 `TripSettingsContent`

职责：

- 纯状态渲染；
- 展示日期输入、影响、忙碌和错误；
- 按状态启用或禁用交互；
- 将用户动作回调给 Route/ViewModel。

Content 不直接调用 repository，不自行重算删除影响。

### 10.5 `AppNavigation`

保持现有目的地和“更多 → 当前旅行设置”路径。本阶段仅补导航行为证据；除非真实测试暴露 callback 或 back stack 缺陷，否则不重构路由结构。

## 11. UI 契约

### 11.1 日期编辑

- 开始日期展示为只读信息。
- 结束日期是唯一可编辑日期。
- dirty 状态下清楚区分当前草稿与已保存范围。
- 增长可以直接提交。
- 缩短必须经过影响确认。

### 11.2 危险确认

确认内容使用稳定的结构化节点，不依赖一整句文案完成测试定位：

- 标题；
- 删除旅行日数量；
- 删除行程项数量；
- 删除 RouteLeg 数量；
- “收藏地点将保留”；
- 取消和确认动作。

自动化通过语义节点和数值断言验证内容，避免因标点或句式微调产生无业务意义的失败。

### 11.3 忙碌状态

- 显示明确进度；
- 不允许修改日期；
- 不允许关闭确认或离开设置页；
- 状态信息不能只依赖颜色；
- 动态进度通过可访问语义暴露。

## 12. 测试设计

### 12.1 JVM ViewModel

必须覆盖：

- Room emission 不覆盖 dirty 草稿；
- 未 dirty 时 Room emission 更新 baseline 和 draft；
- preview 使用固定请求快照；
- 新编辑使旧 preview completion 失效；
- `Applying` 期间日期输入、返回和重复确认不生效；
- 同一 request generation 最多调用一次 apply；
- apply 成功但 Room 确认延迟时保持等待状态；
- 确认前的旧 Room emission 不完成本次请求；
- 匹配的新 Room emission 完成请求并清 dirty；
- Room 流失败后重新同步不重复 apply；
- 旧 collector 结果不能覆盖新 generation；
- 当前旅行被删除时发布返回旅行列表 effect。
- apply 挂起期间先收到匹配 emission、再收到同数量 wrong/reordered IDs 的 fresh mismatch，service 返回后仍不得完成或清 dirty。
- Room 完成匹配对增长、缩短和同尺寸三分支分别覆盖：增长校验 baseline 同序前缀，缩短严格校验 retained IDs，同尺寸严格校验完整 baseline IDs；wrong/reordered 反例均不得匹配。
- 设置页 30 天通过、31 天和极端 `9999-12-31` 被明确拒绝，且拒绝前不调用 deletion counts/apply。

### 12.2 领域与 Room 集成

必须覆盖：

- 增长只在尾部追加连续日期；
- 缩短只删除尾部旅行日；
- preview 后旅行日变化会拒绝旧 apply；
- preview 后行程项或 RouteLeg 数量变化会拒绝旧 apply；
- 缩短范围级联删除被移除日期的行程项和 RouteLeg；
- SavedPlace 保留；
- 剩余旅行日连续重编号；
- 单日删除覆盖相同的级联和重编号；
- 最后一个旅行日不可删除；
- 过期请求失败时没有部分写入。

### 12.3 Compose

必须覆盖：

- 开始日期只读、结束日期可编辑；
- 危险确认使用稳定节点展示精确数量；
- applying 状态锁定输入、确认、取消、返回和外部点击；
- preview/apply 失败保留草稿；
- 快照失效提示重新确认；
- 280dp 宽度和 2× 字体下关键动作可达且触控目标不重叠。

响应式测试只阻断严重裁切、关键操作不可达和交互失效；间距、字体和细小视觉差异留到最终物理真机验收。

### 12.4 导航

必须覆盖：

- 从真实工作台点击“更多”进入当前 trip 设置；
- 返回后仍回到同一 trip 工作台；
- 工作台当前 Tab、Sheet 状态和 Room 内容不被设置往返重置；
- trip 在设置期间被删除时返回旅行列表。
