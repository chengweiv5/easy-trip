## 历史提案：来源覆盖核对与一次定向补查（未实施，不再作为当前推荐规格）

以下保留2026-10-15上一轮提案，便于追溯；其中首次空图统一复核、住宿图不得漏及依赖该规则的调用／检查点要求均被上方当前决定取代。其他条目仍是未批准提案，不代表开发要求。

用户同意先补充此项设计，不代表本规格、后续实施计划、代码开发或Git／手机交付已获批准。本规格补充 `2026-10-15-v3.4-batched-guide-understanding-design.md`；只有本规格明确修改的规则在批准后取代原规则。

## 1. 意图、事实与目标

用户希望一次提交正文和多图供模型理解，不回到逐图串行；高德继续节流。部分素材失败不能使其他有效地点无法手动收藏。当前多图实现已经通过确定性验证，但未通过真实识别质量验收。

此前真实DeepSeek结果及22张实际发送图片的审计见：

- `docs/testing/v3.4.0-batched-guide-understanding.md`
- `/Users/bytedance/.codex/artifacts/easy-trip/v34-batched-guide-implementation-46b4-20261015/quality-audit.json`

关键问题是：一张清晰住宿指南返回合法 `NO_PLACES`，协议校验未失败，却漏掉该图的作者推荐；此外有同地点别名未合并、错字被选为代表名、独立城门漏识别。**接口成功、来源ID齐全、模型自称读完都不能证明地点完整。**

本次目标：

1. 给每张图保留独立的提取／覆盖核对状态，减少“合法空结果”直接被当成完成。
2. 对明确触发的图片最多补查一次，多图仍合并发送；不重发整篇正文或无须补查的图片。
3. 不丢失首次已验证的有效候选，不阻塞其他素材的有效地点进入整理、高德及手动收藏。
4. 明确额外调用成本与仍无法保证的召回边界，不能为保留“永远2次调用”接受已知漏项。

本设计不是OCR真值系统；不承诺发现所有未提取地点，也不承诺任何URL／模型响应永远成功。

## 2. 方案取舍

| 方案 | 优点 | 不采用或保留的原因 |
|---|---|---|
| 仅增加“仔细检查”提示词／相信模型自报完整 | 不增加调用 | 前轮已多次增强提示词仍漏图；同一模型可能同时漏提和错误自评 |
| **所有首次空结果图片复核一次＋有明确信号的非空图片定向补查** | 有可执行的空结果触发规则，复用合并协议，调用有界 | 本规格推荐；纯餐饮／背景图也可能多查一次，必须如实说明成本 |
| 全图独立再扫一遍／新增OCR供应商 | 可提供更独立的证据 | 固定重发所有图片、增加依赖／资源／隐私与调用成本，超出本次范围 |

**选择第二项作为待确认方案。** 不依赖“住宿”“餐饮”分类来免除空图复核，否则住宿图被误分成餐饮时仍会静默跳过。

## 3. 不变与变化

### 保持不变

- 旅行内攻略入口；全局城市优先流程和普通文字／手选图片入口不扩展本功能。
- 100个最终地点、每源100候选／全批400候选、20图、30天，溢出不静默截断。
- 现有实际实现的完整body预算、文件化准备、180秒调用／15秒连接／2MiB响应，普通入口限制不变。仍使用当前配置，不选新模型或供应商。
- 攻略请求共享最多2在途，无700ms间隔；高德700ms／最多2在途，隐私同意门控不变。
- 作者目标证据、底图背景过滤、餐饮／食品排除、住宿保留、多城市不套首城；不凭新增覆盖字段生成地点或执行指令。
- 最终只进行一次纯文字语义整理；不自动收藏、不新建页面／按钮／设置。

### 明确变化

- 首次合法 `NO_PLACES` 的图片不再直接终结：若未用过自动追加机会，补查一次；正文空结果不因此重发。
- 图片的协议格式补救与覆盖补查**共用一次自动追加机会**，不会“格式补救后再覆盖补查”，更不会递归重试。
- “来源候选可用”与“本来源处理完成”分离。补查失败可保留本来源首次已验证候选，同时标出未完成状态。
- 因为空结果图片也复核，常见含餐饮页的攻略可能是**1次初提取＋1次补查＋1次整理＝3次**，不再宣传所有正常帖子都是2次。

## 4. 覆盖信号与准入兼容

保留现有 `sources/sourceId/status/items` 及图片逐字证据规则。每个图片来源允许附加轻量 `coverage`：

| 字段 | 含义 |
|---|---|
| `scan` | `COMPLETE`／`INCOMPLETE`／`UNKNOWN`：模型是否认为已检查本图作者标签、路线停靠、推荐清单与说明段落 |
| `unresolvedNames` | 本图实际可读、但未落实为有效item的名称原字；每个字符串最长100字符、最多100项，遵循现有候选量级 |

- 两个字段都只是模型线索，不是事实认证；`COMPLETE`不能让空图免复核。
- 首次请求要求先逐图完整提取，再检查本图是否还存在未落实的作者目标；不能用短摘要替代完整items，也不能因为先写了coverage就跳过原图阅读。
- 覆盖元数据缺失、附加未知字段、枚举大小写／未知值、格式不合法或超过边界：降为 `UNKNOWN`，不使原本有效items变成协议失败，不截取一段伪称完整。合法字段可单独使用，异常字段不污染其他字段。
- 对非空OK结果，未知／缺失coverage**本身不触发补查**，避免兼容服务不支持扩展字段时整批反复重发。
- `unresolvedNames`不直接成为候选、不进入高德，不从正文或其他图补全。补查后仍须从该原图取得完整item并通过现有校验。
- 空白名称忽略，名称按原字精确匹配；不对线索做模糊纠错、跨城市匹配或类别后缀裁剪。已有有效item的同名线索不是遗漏。
- 覆盖字段按来源隔离；未知／重复来源ID仍按原规则处理，不能借coverage挽救来源事实错误。
- 使用固定通用System Prompt；本次城市、资料、来源清单只在User数据中提供，不硬编码样例城市／地点。

## 5. 确定性触发与自动预算

对**首次请求**的每个来源作如下判定；`followupUsed`由客户端管理，模型不能修改：

| 首次结果 | 自动处理 |
|---|---|
| 图片NO_PLACES，items合法为空 | 覆盖补查一次，不接受分类／自评豁免 |
| 图片OK，coverage.scan为INCOMPLETE | 覆盖补查一次；先保留有效候选 |
| 图片OK，合法unresolvedNames含本源items未覆盖的名称 | 覆盖补查一次；只作为核对重点 |
| 图片OK，缺coverage／UNKNOWN／COMPLETE且无线索 | 不补查；接受当前候选，不声称绝无漏项 |
| 文字／图片可修复格式错误，或来源回执缺失 | 原格式补救一次 |
| 网络、401、429、截断、来源事实不符、UNREADABLE、OVERFLOW | 不自动重发；保留原有失败处理 |
| 已用掉一次自动追加，任何后续结果 | 不再自动发送；终结或保留未完成状态 |

全源／单源异常不能消耗其他来源的预算或撤回其他成功。

### “一次”的精确定义

- 每次**用户显式发送／显式重试产生的处理轮次**，每个来源最多出现于2次HTTP请求：首次＋一次追加，追加原因可以是格式或覆盖，不能两者串接。
- “已发送”按现有SendEvidence判断，不能因超时／响应丢失把次数退回；检查点失败且尚未进入transport可记为未发送，但恢复本身仍不得触发新调用。
- 先按初始分组确定来源集合；每组初次响应后，把其中需要格式补救或覆盖补查的来源合并为**至多1个追加请求**。不同组共用2路门控，组内不逐图串行。
- 请求中逐源声明核对原因；格式来源完整重读，覆盖来源完整复查。两种原因可在同一请求共存。仅发送本组目标图片；正文与明确城市只作上下文，不再次产生正文来源，除非正文自身因格式错误列入目标。
- 新分组测量取首次／混合追加两种完整UTF-8 body的最大值，预留最坏逐源原因标识和通用补查提示；不带首次候选清单或动态长线索进入追加body，避免超过已测预算和引导模型复制旧答案。
- `unresolvedNames`在本地用于判定是否需补查；追加模型重新读原图，不拿线索当真值。使用相同私有图片字节，不重新下载、不模糊压缩、不引入视觉裁剪。
- 若初始分组数为G，提取类HTTP上限为**2G**，没有补查／补救时为G。候选非空时再有一次文字整理；原整理协议格式补救仍可增加一次，必须单列，不藏在“最多一次补查”里。
- 追加失败、超时或返回格式错误不再自动修复。180秒为每次调用上限，**仍受原整批总期限约束**，不延长到无限等待；已过期限只终结未完成来源。
- 任一组返回鉴权／不支持图片，仍阻止尚未发出的组及追加请求；不取消其他已经发送的成功事实。共享slot不能因持久化或诊断异常泄漏。
- 用户点现有重试按钮可开启新显式轮次，重新获得该轮预算；恢复页面、旋转、进程重建、重新订阅状态不算用户重试，不触发网络。

## 6. 来源结果的合并与失败处理

来源必须同时表达：

1. **已接受的候选**：通过名称／城市／来源证据校验的items。
2. **处理状态**：是否仍需核对、自动追加是否已用、未完成原因。

不把“覆盖补查失败”伪装成首次候选证据错误，也不把有候选的来源当成全部完成。

| 追加结果 | 候选与处理状态 |
|---|---|
| OK，items全部按原规则合法，无明确剩余缺口 | 首次候选与新候选按本源字面身份稳定并集，重复证据合并；标为本轮处理完成 |
| 初始空，追加合法NO_PLACES且未报告缺口 | 终结为空；两次都未识别到目标，不标素材失败，但不宣称已证明图中无地点 |
| 初始非空，追加NO_PLACES | 不删除首次合法候选；记结果冲突／待人工重试，不再自动发送 |
| 追加OK但仍报告INCOMPLETE／未覆盖名称 | 接受合法新增候选，保留待核对状态，停止自动补查 |
| 追加网络／鉴权／限流／格式／来源错误／UNREADABLE | 不接受该失败源新增内容；保留首次候选，状态未完成，可显式重试 |
| 格式补救后得到NO_PLACES或新的覆盖缺口 | 自动机会已用，不再补查；空图标未完成，非空候选照常保留 |
| 追加取消／未发送 | 首次有效候选保留；状态取消／未完成，不自动续发 |

- 第二次返回不能删除或悄悄改写首次可信候选。疑似别名仍由后续一次语义整理处理，不在并集阶段猜测。
- 原文字格式补救后合法空结果仍按旧规则完成；上表“空图标未完成”只指图片，不给纯正文增加覆盖重试。
- 每源并集超过100、全批超过400或最终超过100：保留原容量保护，不截断、不以去重提示强迫数量减少；此前已收藏地点不撤销。
- 所有组进入终态后，将可用候选统一整理一次，再查询高德。没有因为组数／补查而新增多轮整理。
- “不阻塞成功收藏”指**本轮终结后**，未完成素材不阻止其余有效结果进入原收藏流程；本设计不承诺补查仍进行中时可抢先收藏，也不新增边处理边收藏。
- 重试只选未完成来源，已有候选、用户手改、已选POI及已收藏项均保留；新增结果增量合并，不替换用户修改、不重复收藏。

## 7. 协议与状态的实施接缝

本轮仅规定职责，不增加通用多阶段框架：

- `GuideBatchProtocol`：提取状态／可选coverage解码；现有items证据验证保持严格。保留原始图片状态供补查判定，不再把NO_PLACES与其他空集合原因提前混为一类。
- 攻略parser内部一个小型覆盖策略module：输入已验证来源结果及已用预算，输出“完成／格式补救／覆盖补查／人工重试”。预算只能由客户端减少，不由模型字段驱动增加。
- `GuideBatchBody`／`Files`／`Scheduler`：精确预留追加开销，重用原图副本及共享两路门控；图片一直保留到该组终态，再清理本轮副本。
- `ParsedSource`保持来源ID及已接受候选，新增可选的覆盖处理记录；不把覆盖状态写进现有`AssistantFailureCode`或`SourceStage`新枚举，以免旧恢复记录解码被打断。
- 内存保留独立的覆盖状态；落盘同时映射为旧枚举可读的非完成progress，必要时附加`UNKNOWN`错误说明。即使可选覆盖字段缺失，也不能把“候选可用但未完整核对”误当成可结束攻略；未知覆盖值保守转人工重试，不执行网络。
- 现有`onSource`从“每源只通知一次”调整为**同源最新快照upsert**：首次保留候选＋待补查快照，终态合并快照。来源顺序稳定、旧代次不可覆盖新批；控制器不能继续把同源快照简单追加到list。
- 集中区分`hasAcceptedCandidates`、`isMaterialComplete`和`needsMaterialRetry`等语义；检视缓存跳过、取消、VM空结果判断、部分收藏、恢复及手动重试，不能继续到处用`failure==null`代表全部含义。
- 普通输入无需覆盖记录，使用默认兼容语义，不更改其调用／重试策略。

### 持久化与取消

- 原version1恢复记录新增**可选**覆盖字段：本来源初始结果已被接受与否、补查原因／状态、一次追加机会是否已用。无该字段的旧记录按旧状态恢复；不对历史完成来源后台补发。
- 使用现有1MiB限制及原子快照写入保护，schema13不变。只要求新代码可读旧记录，不承诺降级旧App能执行新覆盖流程；仍禁止数据库降级。
- 覆盖功能需要一个攻略处理检查点module，供两条入口共用：已有旅行直接粘贴以`tripId＋本地draftId`归属，不伪造全局创建handoff；从全局创建交接的攻略继续用其真实operationId／attempt。不只在`activeGuide != null`时保存，否则直接粘贴入口会被遗漏。
- 检查点复用version1状态编码／1MiB和现有私有文件、原子写机制，持久化本地draft归属与单调revision。原图按本地ID存入该草稿私有范围，能从恢复记录精确关联；通用图片启动清理不得删掉仍被此记录引用的素材。正文／城市／候选不复制进额外DB表。
- 首次已接受候选与待补查状态须有可恢复快照；parser收到持久化成功回执后才允许追加发起。追加前原子消费本轮机会；若检查点不能安全写入，**不发送自动补查**，保留内存结果／原有效记录并显示保存未完成，交给显式重试，不循环保存。普通输入不接此检查点，不引入全应用通用工作流引擎。
- 可恢复记录中处理未完成但尚无候选时，也必须保存原分享、图片与已消耗机会；不再以`items.isEmpty()`／候选为空直接丢掉覆盖状态。与原空结果显式重试语义共同验收。
- 进程重建时，将正在补查／发送未知的状态映射为未完成，保留已接受候选，不自动重放。手动重试是一轮新授权，不伪装成恢复原未知请求。
- 不在全局城市识别阶段提前做地点识别；新建旅行交接的原分享只领取一次。取消／导航离开后不得有迟到响应覆盖新批。
- 将小型可恢复快照与原图／body生命周期分开；不把Base64、body或原模型响应放入Room／恢复JSON。
- 检查点持久化不能为了写入中间快照提前把global handoff改成已完成：运行中保留其正在处理语义，终态以原CAS确认状态。直接粘贴的归属索引不能从模型提供的路径／ID构造。
- 全部处理完成且收藏成功、用户明确放弃草稿或删除所属旅行后才释放对应记录／原图；部分收藏保留它们。完成后重开不复活旧草稿；只清理已核验归属的文件，原1MiB写失败不破坏上一有效记录。
