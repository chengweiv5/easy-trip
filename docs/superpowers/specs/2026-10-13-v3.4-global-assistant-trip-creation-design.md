## 1. 已确认的用户意图

用户经常先发现攻略，再考虑创建旅行。助手不能要求用户先进入一个不相关的已有旅行，才能识别新攻略和创建另一趟旅行。

- 一个助手、两个入口：首页可直接进入，无旅行也可用；旅行内保留快捷入口，默认补充当前旅行。
- 首页助手不绑定最近打开的旅行；地图候选预览不需要先保存一趟空旅行。
- 用户确认旅行信息与所选地点后，创建旅行并收藏；后续手动安排，不自动按天排行程。
- **日期可选。** 用户在自然语言中提供日期时可自动识别、预填，并允许修改或清空；未给日期也能创建。
- 本文把用户所说“自然语音输入”理解为自然语言文字，包括语音输入法的转写；不恢复App内录音、语音识别、麦克风权限或语音对话需求。
- 不新增会话列表、聊天首页或第三个底部导航目的地。保留手动创建旅行、现有旅行导航和设置入口。

本节是已确认方向；以下是据此形成的具体设计，需用户评审后再编写实施计划，不能沿用v3.3的开发授权。

## 2. 方案选择

| 方案 | 判断 |
| --- | --- |
| 先创建空旅行，再进入旅行助手 | 拒绝。流程倒置，取消／失败容易留下无用旅行。 |
| 首页与旅行内各做一套助手 | 拒绝。输入、过滤、候选及重试容易产生差异。 |
| 共用识别与候选会话，区分保存目标 | 采用。无旅行先准备素材和地图候选，有旅行则保留现有直接收藏。 |

这不是把整套产品换成聊天，而是解除“助手必须依附已保存旅行”的限制。

## 3. 入口、页面与提交动作

### 3.1 首页进入

“我的旅行”标题下提供“从攻略创建旅行”卡片，在有旅行、无旅行和旅行列表加载失败状态都可进入；手动“创建新旅行”保留。入口位置与尺寸已落入Pencil G01/G02/G22，等待UI评审，不在源码中先行开发。

首页打开独立的助手页面，包含输入、处理状态、候选列表和地图；复用当前助手组件与选择操作，不展示虚构的旅行标题或最近旅行名称。

全局助手标题栏保留48dp的现有模型设置入口，不新增第二套设置页。未配置时先去设置，返回保留输入，仍由用户手动开始识别；处理中设置禁用，先取消处理后才能修改配置，不能在旧批次中混用新配置。

流程：

1. 输入文字／图片，或粘贴携程、小红书分享文案／URL，可附加自己的旅行计划。
2. 用户点击处理后才联网；读取、识别、城市核对与地图查询均发生在临时会话。
3. 展示地图候选，允许修改城市、地点和选择；至少选择一个有效地点后，进入“创建旅行”信息确认。
4. 旅行名称必填并允许修改，日期可空，保留现有出行方式设置。确认区显示所选地点数，可返回修改，返回不丢候选。
5. 最终“创建并收藏”才执行持久写入。成功后进入新旅行地图，显示已收藏地点，不把地点自动分配到某一天。

不增加独立回执页面；不在零有效地点时创建空旅行。确实只想手动建旅行的用户使用原有入口。

### 3.2 旅行内进入

保留地图上的助手入口、当前旅行上下文与原来“选择→收藏”的路径。目标固定为当前旅行，不新增旅行选择确认，不突出“创建另一趟旅行”。

处理成功仍按v3.3清空本批输入、图片与候选并开始新一轮，保留当前旅行与已收藏地点。无旅行会话与旅行内会话不共享输入、选择或过期回调。

旅行内输入出现新日期时，不因此修改当前旅行日期；v3.4日期识别仅用于新旅行草稿。

### 3.3 退出与恢复

未修改的空会话可以直接退出；有输入、图片、候选或旅行信息修改时，退出提示保留当前查看或放弃本轮，不提前写入旅行。

旋转／窗口调整保留当前会话；系统杀进程后，不伪装已经恢复失效图片或正在进行的模型请求，沿用明确提示和重新提供素材的边界。仅最终提交操作另有持久化恢复机制，见第7节。

## 4. 素材、目的地与地点

- 保持v3.3的平台与资源范围：携程社区、小红书；一批一条链接，最多20图、30个最终地点，独立体积／像素／超时限制不变。原有文字、图片路径继续复用，不新增其他平台。
- 链接路径沿用作者证据、语义去重、剔除食品和全部餐饮地点、保留非餐饮地点及独立子地点的规则；不扩大普通手动输入的过滤范围。
- 用户明确指定的目的地优先；未指定时从攻略正文／作者标注推断目的地，并在地图查询前允许核对。没有旅行上下文时不直接拿手机所在城市作为旅游目的地，也不读取最近旅行城市兜底。
- 地点已有明确城市时按各自城市查询；多个已明确城市可以共存，标题可由已选择地点的城市给出可编辑建议。跨城市同名地点不合并。
- 不能判断城市的地点先澄清或留待核对；不能为方便而把多城市攻略全部套进一个城市。用户可以先选择已准确匹配的地点创建，未选择／未匹配项不写入。
- 模型只能建议名称、城市与日期元数据；坐标仍来自地图候选，用户确认才产生保存命令。名称和城市建议不能授予模型数据库写入权。
- 用户手动修改旅行名称、日期或城市后，异步结果不能覆盖；重新识别应保留手工值，用户明确选择重新采用建议时才替换。

## 5. 日期与天数

### 5.1 可选及自动预填

不设置日期时以`startDate=null`创建未定日期旅行；不默认今天或攻略发布日期。日期识别失败不阻断地点处理或无日期创建。

日期来源只使用**用户为本次旅行表达的意图**：

- 允许：用户输入“2026年10月24日到26日去青州”、补充“明天出发，玩三天”，或语音输入法转写的等价文字。
- 排除：攻略作者的出游时间、帖文发布时间、图片水印、URL中的`shareTime`、分享标题“三日游路线”等。攻略内容是资料，不是用户日程指令。
- 完整分享文案中无法区分用户补充和平台标题时，先保留原文供核对，不直接预填日期。即使用户要求“照这篇攻略”，没有明确日历日期也不将作者日期变成用户日期。

系统提示词为固定、通用模板；旅行地名和日期例子只在测试样例或本次用户数据中，不能写进固定提示词。模型返回来源片段与结构化日期表达，本地校验来源和日期范围；没有来源依据不接受。

### 5.2 明确日期、相对日期与歧义

每次用户发起处理时记录设备时区与参考日期，在同一批次和重试中保持不变；不读取网页时间作为参考。结果显示完整年月日，不能只显示“明天”。

明确绝对日期或可唯一计算的相对表达可以预填；例如以**2026-10-13、Asia/Shanghai**为参考，“明天出发，玩三天”对应**2026-10-14至2026-10-16**。这是测试锚点，不是固定到代码中的日期。

缺少年份时仅在参考年份能给出无歧义结果时形成建议；已过去、跨年或多个解释均合理时请求核对，不偷偷顺延一年。“下周五”按本地周一至周日定义计算并展示实际日期；单独“周末”“国庆前后”“有空去”等不生成确定日期。

日期冲突、无效日期、结束早于开始、时区不确定或天数超限时显示对应提示，允许改正或清空日期继续。旧批次结果不能覆盖当前输入，配置变化／取消后不能继续提交日期结果。

### 5.3 日期不等于自动排程

沿用旅行最少1天、最多30天的约束：

- 无日期且无明确游玩天数：先建1个空白日；确认时说明“先收集地点，后续可添加天数”。
- 用户明确说“玩三天”但没有出发日期：可建议3个无日期空白日，用户可改；不从攻略标题自动采用天数。
- 有完整起止日期或“开始日期＋天数”：按包含首尾日计算1–30个空白日，并显示供确认。
- 只有明确出发日期、没有结束日期或天数：预填出发日，确认时明确显示“暂按1天建立，可修改”；这是可见的初始天数，不宣称已识别返程日期。
- 用户清空日期时保留已确认的天数，不用自动识别重新填回；天数没有确认过则保持默认1天。

无论日期和天数是否确定，所有新地点都只加入地点池，不生成行程项、时间安排、交通方案或费用。

### 5.4 编辑控件与校验

- G33日期面板：先选开始日、再选结束日；允许只确认开始日，未给天数时明确暂按1天。取消只丢弃面板内未确认修改；清空日期返回G32并保留已确认天数。结束早于开始或跨度超过30天时就地提示、禁用确认、保留原草稿。
- G34天数面板：数值可输入并配减／加按钮，范围1–30；1时减号禁用，30时加号禁用。无日期时只改变空白日数；有开始日时确认前明确展示重算后的结束日，确认才覆盖日期范围。
- G35表单错误：名称去除首尾空白后不能为空，天数与日期必须有效；错误就地显示并定位、读屏播报首项。禁止提交但不清空地点和其他输入，不重新调用模型。

## 6. 代码事实与模块设计

以下事实已从当前源码读取，不代表v3.4已经实现：

| 当前事实 | v3.4处理 |
| --- | --- |
| `AppNavigation`在旅行路由以`tripId`创建`PlaceAssistantViewModel`；控制器也要求`tripId` | 将识别会话与保存目标分离，允许无旅行会话；禁止用假ID占位。 |
| `TripListContent`已有手动新建和设置入口，没有全局助手入口 | 新增导航入口，复用现有主题和基础组件。 |
| `CreateTrip.startDate`为可空；无日期手动创建默认1天，`RoomTripRepository`写入`TimeMode.DRAFT` | 复用已有未定日期语义；仅新增助手草稿预填和已确认天数，不为日期可选单独改schema。 |
| `TripDao.createTripWithDaysIdempotent`保护单次创建；`RoomPlaceImport`有事务和导入回执 | 组合成“创建＋收藏＋回执”的单事务能力，不能在UI中先后调用两个独立提交。 |
| `assistant_import_receipts`已有operationId、tripId、digest、resultsJson | 以版本化新建操作命名空间及完整命令摘要复用，旧旅行导入协议保持兼容。 |

建议模块：

1. **AssistantSession**：持有输入、来源、候选、选择与处理代次；不依赖已保存旅行。目标显式区分`NewTripDraft`与`ExistingTrip(tripId)`，会话创建后固定，避免进行中请求写错目标。
2. **TripDraftInterpreter**：只提取旅行名称、目的地和用户日期意图；与地点提取、地图查询分工清晰。复用同一模型配置、取消和超时机制；不得让日期失败重复调用成功的全部图片识别。
3. **CreateTripFromIntake**：接收经过验证的旅行元数据和所选地图POI，隐藏事务、幂等回执与恢复细节；现有旅行仍调用原收藏接口。
4. **页面宿主**：首页独立助手宿主与旅行工作台宿主复用输入／候选组件。仅宿主决定保存动作和成功导航，不复制解析规则或构造“伪旅行工作台”。

只拆解受本功能影响的旅行依赖，不重写全应用导航或通用Agent框架。元数据推理每批最多1次请求，沿用45秒单请求保护，无自动重试；用户明确重试元数据时不重跑成功图片。具体真实验收调用预算在实施计划中列明，不承诺离线推理。

## 7. 创建、幂等与中断

用户最终确认时生成不可变命令：会话操作ID、待创建旅行ID、名称、可选日期、天数、出行方式、所选POI及来源。摘要覆盖上述全部业务字段，不能只校验地点列表。

- 执行前校验名称、1–30天、日期一致性、1–30个可收藏地点、有效坐标、用户选择、去重结果和当前配置／会话代次。
- 在**同一个Room事务**中创建旅行、空白日、所选收藏及导入回执；没有任何网络或模型调用放进事务。
- 任一步失败整体回滚，旅行列表和地图不会观察到半成品空旅行。创建过程中锁定重复点击和可变输入，失败保留原草稿。
- 同一操作ID与同一摘要只返回同一已提交结果；同ID不同摘要拒绝。用户改动后开启新操作，而不是覆盖旧回执或旧旅行。
- 新建操作使用独立版本前缀，摘要包含旅行元数据；复用现有回执表时不改变旧旅行导入的摘要语义。旧回执查询与解码必须回归。
- 提交前将最小恢复记录写入App私有存储并原子落盘，内容只含操作ID、规范化最终命令和摘要，不含API Key、原图或完整网页。仅保留一条未解决的新建操作，完成回读后清理。
- 中断恢复先查询回执：已提交则打开同一旅行；未提交则恢复确认供用户重试，不能自动再发模型请求或后台创建。
- 已提交旅行被用户后来编辑时只返回原回执，不重复校验创建原值后覆盖后续修改；后来删除时提示该旅行已不存在，不重新生成。
- 取消／退出发生在提交附近时以持久回执为准；不能同时报告“未创建”并留下成功旅行。确认成功后清理本批图片，只清理本会话持有的文件。

该设计优先复用schema11，不在设计阶段修改数据库版本。若实现发现必须变更schema，先修订设计和迁移验收，不降低数据库版本。

## 8. 验收门禁

### 功能及失败路径

- 设备上从无旅行首页可进入助手、识别攻略、选择地点、无日期创建并进入新旅行；此前旅行数为0，成功后为1。
- 有旅行首页进入不会默认绑定最近旅行；旅行内原收藏流程不增加创建步骤、不改变当前旅行日期。
- 携程、小红书各一条公开样例走真实生产链，识别、过滤、地点选择后创建新旅行；只有用户最终确认才写入。
- 两入口相互独立，旧图片清理、城市查询和模型结果不污染新会话；退出、旋转和进程中断结果诚实。
- 失败、取消、重复点击、同ID不同摘要、提交完成后进程退出、后来编辑／删除旅行均覆盖；事务故障注入验证零半成品。

### 日期

- 纯链接无用户日期、帖子日期／水印／shareTime、攻略标题“三日游”均不自动设置用户日期或天数。
- 绝对日期、相对日期、开始日＋天数、仅天数、仅开始日、缺少年份、跨年、闰日、冲突与超过30天分别验证。
- 固定参考日期／时区的重试不会改变结果；设备时区／日期变化只影响新批次。人工修改和清空优先。
- 日期解析失败时地点结果保留，允许无日期创建；旅行内输入日期不改现有日期。

### UI、回归与隐私

- Pencil覆盖首页有／无旅行入口、全局输入、缺目的地、候选、无日期确认、自动日期建议、歧义／失败、创建中及恢复状态；同时覆盖已有旅行入口不变。
- 320dp、2倍字体、键盘、长旅行名、30条候选及AA–AD、20图、TalkBack和返回行为均列入相关设备验收；未执行项不得称通过。
- 对共享候选、城市规则、相机视角、保存后新轮、旧回执、手动建旅行、日历与费用显示执行回归，不仅测新页面。
- 地图和模型真实测试使用隔离旅行和显式预算，不碰用户生产旅行，不读取不相关凭据；安装和发布需单独授权。
